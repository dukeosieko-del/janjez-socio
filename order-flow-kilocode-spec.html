Scope

Everything up to and including the M-Pesa checkout already exists and is out of scope. Kilo Code's work begins the moment payment succeeds: capture the order, write the confirmation record, and log it for support/dispute reference.

Decision logic — when the micro-category branch fires

The branch is real, not cosmetic. Whether it fires depends on how many SKUs the selected subcategory resolves to:

  • 1 SKU → skip straight to the order form (link + quantity). Most subcategories are this shape — e.g. Facebook Comments, Twitter Poll Votes.
  • 2+ SKUs → show the micro-category list first, user picks exactly one, then the order form. Examples: WhatsApp Channel Post Reactions (22 emoji options), TikTok Real & Permanent Likes (4 fixed bundles), most "Recommended / Quick Boost / Premium Shield" tiered services.

Order form fields (before checkout)

FieldNotes
linkProfile/post/channel URL. Note: a small number of SKUs repurpose this field to collect a phone number instead of a URL — flag any SKU where fulfillment is manual rather than automated.
quantityEither a preset button value (100/500/1,000/2,500/5,000) or a custom numeric entry within the SKU's min/max range.
quantity_sourceWhether quantity came from a preset or custom input — worth logging distinctly (see open question below).
computed_priceLive-calculated from unit price × quantity, shown before checkout.

Open questions before building the logging step

1. Quantity source — should presets and custom quantities be logged identically, or does quantity_source need to be distinct for reporting/fraud checks?
2. Refill guarantee flag — should this be pulled onto the order record at time of purchase (so it's locked in for later disputes), or looked up live from the SKU each time support needs it?
